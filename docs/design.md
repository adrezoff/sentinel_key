## 1. Назначение и основные принципы

Разрабатываемая система предназначена для автоматического обнаружения потенциальных секретов в Git-репозиториях: API-ключей, токенов доступа, паролей, приватных ключей, credentials и других чувствительных данных. Система должна анализировать не только текущее состояние репозитория, но и его историю, поскольку секрет может быть удалён из последней версии файла, но остаться доступным в предыдущих коммитах.

Основная архитектурная идея заключается в многостадийном анализе: сначала из Git извлекается только необходимая информация, затем из изменений выделяются потенциально чувствительные значения, после чего они проходят несколько дешёвых локальных детекторов. Только наиболее подозрительные кандидаты передаются в LLM для дополнительной классификации.

Такой подход позволяет одновременно решить три проблемы: уменьшить объём обрабатываемых данных, не отправлять в LLM весь репозиторий и снизить количество ложных срабатываний.

Система строится как асинхронный pipeline. Операции ввода-вывода — получение данных из Git, обращения к LLM и работа с хранилищем — выполняются через `asyncio`. CPU-зависимые операции, например вычисление энтропии и часть анализа токенов, выносятся из event loop в `ThreadPoolExecutor`. Такое разделение соответствует требованиям проекта и не позволяет вычислительным задачам блокировать остальные стадии обработки.

В упрощённом виде систему можно представить следующим образом:

```text
Git Repository
      │
      ▼
Commit / Diff Collection
      │
      ▼
Added Lines
      │
      ▼
Candidate Extraction
      │
      ▼
Regex + Entropy + Context
      │
      ▼
Risk Scoring
      │
      ├── низкий риск → пропуск
      │
      └── высокий риск
              │
              ▼
             LLM
              │
              ▼
          Classification
              │
              ▼
       Findings + State
```

При этом отдельные компоненты не должны смешивать ответственность. Git-слой занимается только получением данных, анализатор — только обработкой содержимого, LLM-слой — классификацией, а storage — сохранением состояния и результатов.

# 2. Работа с Git и инкрементальная обработка

Одной из главных особенностей системы является необходимость анализировать историю Git. При этом простой подход с хранением только `last_processed_commit` ненадёжен, потому что Git представляет собой граф, а не линейную последовательность коммитов. В истории могут присутствовать merge-коммиты, разные ветки, rebase и переписанная история.

Поэтому состояние системы должно строиться на **SHA коммитов**. Для каждого репозитория хранится множество уже обработанных commit SHA. При следующем запуске система получает актуальную историю Git, сравнивает её с сохранённым состоянием и передаёт в pipeline только ещё не обработанные коммиты.

Это одновременно решает проблему первого запуска и последующих запусков.

### Первый запуск

Если состояние отсутствует, система получает всю доступную историю репозитория, например через `git rev-list --all`, формирует множество SHA и запускает полный анализ. Большую историю не следует обрабатывать одним огромным набором: коммиты передаются в pipeline небольшими порциями, что позволяет ограничить использование памяти и организовать параллельную обработку. После успешного анализа коммиты отмечаются как обработанные.

Для небольшого учебного проекта состояние можно хранить в `state.json`, однако более надёжным вариантом является SQLite. В базе можно хранить commit SHA, родительский коммит, статус обработки и время завершения анализа.

### Последующие запуски

При повторном запуске система снова получает SHA из Git и проверяет их наличие в storage:

```text
Git history
    │
    ▼
All commit SHA
    │
    ▼
Compare with processed SHA
    │
    ├── already processed → skip
    │
    └── new → analysis pipeline
```

Таким образом, после первого полного сканирования анализ становится инкрементальным. Система не зависит от даты коммита и не предполагает, что история всегда линейна. SHA является естественным идентификатором Git-объекта и позволяет сделать обработку идемпотентной.

Важно также обеспечить идемпотентность результатов: повторная обработка одного коммита не должна создавать одинаковые findings. Для этого можно использовать уникальный ключ вида:

```text
(commit_sha, file_path, line_number, detector)
```

# 3. Получение diff и выделение кандидатов

После определения списка коммитов система получает diff каждого нового коммита. Полный анализ содержимого каждого файла не требуется: основной интерес представляют изменения, внесённые конкретным коммитом.

В первую очередь анализируются **добавленные строки**. Например:

```diff
 API_URL = "https://api.example.com"
+API_KEY = "AKIAIOSFODNN7EXAMPLE"
```

Из diff система должна получить структурированный объект:

```text
commit_sha
file_path
line_number
operation = ADD
content
context
```

Удалённые строки обычно не передаются в основной детектор, поскольку они не представляют нового риска текущего изменения. Такой подход одновременно уменьшает объём данных и позволяет точно связать найденный секрет с конкретным коммитом и строкой.

После выделения добавленных строк выполняется не просто лексическое разбиение текста, а **извлечение потенциальных секретных значений**.

Например:

```text
DATABASE_PASSWORD = "superSecretPassword123"
```

можно представить как:

```text
key   = DATABASE_PASSWORD
value = superSecretPassword123
```

Для HTTP-заголовка:

```text
Authorization: Bearer eyJhbGciOiJIUzI1Ni...
```

полезнее получить:

```text
key   = Authorization
type  = Bearer token
value = eyJhbGciOiJIUzI1Ni...
```

То есть задача tokenizer/candidate extractor — не разбить строку на слова ради самого разбиения, а выделить **структурированные значения, которые потенциально могут являться секретами**.

Для этого вводится единая модель `SecretCandidate`:

```text
SecretCandidate
├── commit_sha
├── file_path
├── line_number
├── key
├── value
├── source_line
├── token_type
├── entropy
├── regex_matches
└── score
```

Такая модель становится основным объектом, который передаётся между стадиями анализа. Она содержит как исходную информацию, так и признаки, полученные детекторами.

# 4. Многоуровневое обнаружение секретов

Главная идея detection layer — не пытаться определить секрет одним алгоритмом. Вместо этого система собирает несколько независимых признаков и объединяет их в итоговый риск.

Первый уровень — **регулярные выражения**. Regex позволяет быстро находить известные форматы: AWS-ключи, GitHub-токены, JWT, Slack-токены, private keys, Bearer tokens, database URLs и различные варианты API keys/passwords. Такой детектор очень дешёвый, поэтому он выполняется локально до обращения к LLM.

Второй обязательный уровень — **энтропия Шеннона**. Для строки вычисляется:

```text
H(X) = - Σ p(x) log₂ p(x)
```

Интуитивно низкоэнтропийные строки обычно содержат много повторяющихся символов, тогда как случайно сгенерированные токены имеют более высокое разнообразие символов. Поэтому высокая энтропия может быть дополнительным признаком случайно сгенерированного секрета.

Однако энтропия не является доказательством наличия секрета. UUID, hash, minified JavaScript и другие обычные данные также могут иметь высокую энтропию. Поэтому она используется только как один из признаков.

Третий источник информации — **контекст**. Например, одинаковая строка:

```text
a8F$2kL91xQp7Z
```

может быть обычным тестовым значением, а может находиться в:

```text
DATABASE_PASSWORD = "a8F$2kL91xQp7Z"
```

Во втором случае вероятность секрета значительно выше. Поэтому учитываются имя переменной, тип токена, путь к файлу и окружающий код.

Все признаки объединяются в risk score:

```text
risk =
    regex_score
    + entropy_score
    + context_score
    + token_type_score
```

Конкретные коэффициенты должны быть конфигурационными, а не жёстко зашитыми в коде.

Например:

```text
Regex match              +0.5
Высокая энтропия         +0.2
Название secret/password +0.2
Чувствительный контекст  +0.1
--------------------------------
Итого                     1.0
```

Полученный score используется для маршрутизации кандидата:

```text
низкий риск       → игнорировать
средний риск      → suspicious / сохранить
высокий риск      → отправить в LLM
```

Таким образом, LLM не заменяет классические детекторы, а работает как дополнительный уровень проверки. Это принципиально важно: отправлять в LLM каждую строку репозитория дорого и неэффективно. Сначала дешёвые локальные методы значительно сокращают пространство поиска, и только затем наиболее интересные кандидаты передаются модели.

# 5. Асинхронный pipeline и параллельная обработка

Выполнение системы организуется как pipeline с асинхронными очередями между стадиями. Это позволяет отделить скорость получения коммитов от скорости их анализа и не загружать память неограниченным количеством задач.

Например:

```text
Git Collector
      │
      ▼
commit_queue
      │
      ▼
Commit Workers
      │
      ▼
Diff → Tokenizer → Regex/Entropy
      │
      ▼
candidate_queue
      │
      ▼
LLM Workers
      │
      ▼
Result Processor
      │
      ▼
Storage
```

Для очередей используется `asyncio.Queue` с ограниченным размером:

```python
commit_queue = asyncio.Queue(maxsize=100)
candidate_queue = asyncio.Queue(maxsize=500)
```

Ограничение размера реализует **backpressure**. Например, если Git быстро создаёт кандидатов, а LLM обрабатывает их медленно, система не будет бесконечно накапливать объекты в памяти — producer будет ждать освобождения места в очереди.

Асинхронность применяется прежде всего к I/O:

```python
async def process_commit(commit):
    diff = await git.get_diff(commit)
    result = await analyzer.analyze(diff)
    await storage.save(result)
```

CPU-bound операции выполняются вне event loop:

```python
result = await asyncio.to_thread(
    calculate_entropy,
    value
)
```

либо через явно созданный `ThreadPoolExecutor`:

```python
executor = ThreadPoolExecutor(max_workers=4)
```

Таким образом, `asyncio` отвечает за координацию большого количества ожидающих операций, а пул потоков — за выполнение вычислительных задач, которые иначе могли бы блокировать event loop.

Количество worker'ов должно быть конфигурационным. Например:

```text
Git workers   = 4
CPU threads   = 4
LLM workers   = 5
```

Для LLM дополнительно используется semaphore, чтобы система не отправляла сотни запросов одновременно:

```python
llm_semaphore = asyncio.Semaphore(5)
```

Это позволяет контролировать нагрузку, стоимость и latency.

# 6. LLM-классификация и безопасность

LLM используется как **финальный классификатор подозрительных кандидатов**, а не как основной механизм поиска. На вход модели передаётся не весь repository и не весь commit, а конкретный кандидат с необходимым контекстом:

```text
Repository
Commit SHA
File path
Line number
Source code
Detected token
Entropy
Regex matches
Context
```

Контекст необходим, потому что сама строка редко позволяет однозначно определить, является ли значение секретом.

Например:

```text
DATABASE_PASSWORD = "..."
```

значительно информативнее, чем просто:

```text
"superSecretPassword123"
```

LLM должна вернуть структурированный результат:

```json
{
  "is_secret": true,
  "secret_type": "database_password",
  "confidence": 0.96,
  "severity": "high",
  "reason": "The value is assigned to a database password variable.",
  "recommendation": "Rotate the credential and remove it from Git history."
}
```

Модель должна учитывать имя переменной, окружающий код, формат значения, энтропию, результаты regex, путь к файлу и контекст репозитория. При этом ни высокая энтропия, ни совпадение regex сами по себе не должны считаться достаточными основаниями для положительной классификации.

### Prompt

Системный prompt должен задавать модели роль security-классификатора, определять понятие секрета и требовать строго структурированный JSON. Важно явно перечислить типичные false positive: UUID, hash, timestamps, тестовые данные, placeholders, публичные значения конфигурации и обычные случайные строки.

Пользовательская часть prompt формируется динамически:

```text
Repository: {repository}
Commit: {commit_sha}
File: {file_path}
Line: {line_number}

Code:
{source_line}

Context:
{context}

Detected token:
{token}

Entropy:
{entropy}

Regex matches:
{regex_matches}

Determine whether this value is a real or potentially real secret.

Return only JSON.
```

Полный системный prompt из исходного документа можно использовать практически без изменения, поскольку он уже задаёт необходимую классификацию и формат ответа.

### Защита самого анализатора

Отдельная проблема заключается в том, что анализатор сам обнаруживает секреты и потенциально может отправить их во внешний LLM. Поэтому желательно перед передачей данных использовать маскирование:

```text
Исходное значение:
AKIAIOSFODNN7EXAMPLE

В LLM:
AKIA...EXAMPLE
```

При этом исходный кандидат хранится локально и связывается с результатом через внутренний `candidate_id`.

В production-варианте также должна существовать возможность полностью отключить передачу содержимого во внешние LLM.

# 7. Хранение результатов, ошибки и итоговая архитектура

Storage отвечает за две разные группы данных: **состояние обработки** и **результаты анализа**.

Состояние репозитория содержит:

```text
RepositoryState
├── repository_id
├── processed_commits
├── last_scan
└── version
```

Результат анализа представляет собой `Finding`:

```text
Finding
├── finding_id
├── commit_sha
├── file_path
├── line_number
├── secret_type
├── confidence
├── severity
├── detector
├── created_at
└── status
```

Поле `detector` позволяет понимать, каким способом был обнаружен объект:

```text
regex
entropy
regex+entropy
regex+entropy+llm
```

Для большого количества коммитов целесообразно использовать SQLite, поскольку он позволяет одновременно хранить историю обработки, результаты и обеспечивать уникальность записей. Для небольшого прототипа допустим `state.json`.

Ошибки отдельных стадий не должны останавливать обработку всего репозитория. Ошибка Git может привести к пропуску конкретного коммита, ошибка diff — к пропуску конкретного файла, а ошибка LLM должна переводить соответствующий кандидат в состояние `LLM_FAILED`.

Для сетевых ошибок LLM используется ограниченное число повторных попыток с exponential backoff:

```text
1 sec → 2 sec → 4 sec → 8 sec
```

После превышения лимита попыток результат помечается как ошибочный, но остальные кандидаты продолжают обрабатываться.

## Итоговая модель

Таким образом, вся система сводится к четырём логическим уровням:

```text
┌─────────────────────────────────────┐
│ INPUT                               │
│ Git repository                      │
└──────────────────┬──────────────────┘
                   │
                   ▼
┌─────────────────────────────────────┐
│ COLLECTION                          │
│ history → commits → diff → lines   │
└──────────────────┬──────────────────┘
                   │
                   ▼
┌─────────────────────────────────────┐
│ DETECTION                           │
│ tokenization → regex → entropy     │
│ → context → risk scoring            │
└──────────────────┬──────────────────┘
                   │
                   ▼
┌─────────────────────────────────────┐
│ CLASSIFICATION                      │
│ LLM verification of suspicious      │
│ candidates                          │
└──────────────────┬──────────────────┘
                   │
                   ▼
┌─────────────────────────────────────┐
│ STORAGE                             │
│ findings + state + logs + metrics  │
└─────────────────────────────────────┘
```

Ключевое архитектурное решение состоит в том, что **LLM является последним уровнем проверки, а не центром всей системы**. Git предоставляет историю, diff сокращает объём данных, tokenizer выделяет кандидатов, regex и entropy быстро формируют признаки, risk scoring определяет необходимость дополнительной проверки, а LLM принимает финальное решение по наиболее подозрительным случаям.

Такой дизайн позволяет получить систему, которая одновременно является инкрементальной, параллельной, асинхронной и относительно экономной по вычислительным ресурсам. Первый запуск выполняет полное сканирование истории, последующие — только новых коммитов; состояние строится по SHA, а не по времени; pipeline разделён очередями и worker'ами; CPU-bound операции не блокируют event loop; а результаты анализа сохраняются независимо от жизненного цикла конкретного запуска.
