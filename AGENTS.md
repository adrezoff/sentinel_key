# AGENTS.md

Инструкция для ИИ-агентов (и людей), работающих с репозиторием **sentinel_key** — системой поиска секретов в Git-репозиториях и их истории.

> Прочитай файл целиком до первого изменения. Источники истины: `docs/models.md` (модели и поля), `docs/modules.md` (модули), `docs/design.md` (исходный дизайн-док). При расхождении кода и документации сначала исправляется документация, затем код.

## 1. Что делает система

Асинхронный многостадийный pipeline:

```
Git → diff (добавленные строки) → preprocessor (RawCandidate)
    → static_analyzer: regex + entropy + context → risk score
    → route: IGNORE | SUSPICIOUS | AI_VALIDATION (задача в ленте)
    → ai_validation: вердикт LLM
    → incident_manager: Incident (если высокая вероятность утечки credentials)
```

Ключевая идея: **LLM — последний уровень проверки, а не центр системы.** Дешёвые локальные детекторы отсекают подавляющее большинство строк. Вся работа оформлена как **задачи в ленте** (`Task`), запуск анализа — корневая задача `REPOSITORY_SCAN`.

## 2. Стек и окружение

> **Статус: проект на стадии проектирования.** Кода, `pyproject.toml` и выбранных библиотек пока нет.

**Решено (из дизайн-дока)**
- Python **3.11+**.
- `asyncio` для I/O; CPU-bound операции (энтропия и т.п.) — `ThreadPoolExecutor` / `asyncio.to_thread`.
- Целевое хранилище — SQLite (для самого раннего прототипа допустимо временное упрощение, но модели и схема проектируются под SQLite).
- Git вызывается как внешний процесс через `asyncio.create_subprocess_exec` (без `shell=True`).

**Не выбрано (не предполагай, не добавляй молча)**
- драйвер SQLite и способ доступа из `asyncio`, менеджер зависимостей, структура `pyproject.toml`;
- LLM-провайдер, модель и клиент;
- фреймворк тестов и инструменты качества (кандидаты: `pytest`, `pytest-asyncio`, `ruff`, `mypy`);
- способ запуска демонов и интерфейс запуска анализа (CLI/API).

**Правила, пока стек не утверждён**
1. Не добавляй сторонние зависимости без согласования. Если без библиотеки не обойтись — опиши выбор (варианты, плюсы/минусы) в `docs/decisions/NNNN-*.md` и дождись решения.
2. Предпочитай стандартную библиотеку.
3. Пиши код за интерфейсами (`Feed`, `LlmClient`, `Notifier`, `Storage`), чтобы выбор библиотеки не размазался по проекту.
4. Не создавай `pyproject.toml`, CI и конфиги линтеров по своей инициативе — это отдельная задача «bootstrap проекта».

**Команды.** Единых команд сборки, запуска и тестов пока нет; раздел заполняется после bootstrap-задачи.

## 3. Структура репозитория

```
sentinel_key/
  AGENTS.md
  docs/
    design.md          # исходный дизайн-док
    models.md          # модели и поля
    modules.md         # модули и компоненты
    decisions/         # ADR: выбор библиотек и инструментов
  src/                 # исходники
    models/            # один файл — одна модель; подпакеты repository/task/candidate/incident
    config/            # конфигурационные модели, загрузка конфигурации
    git_collector/     # история и diff из Git
    preprocessor/      # diff → RawCandidate
    static_analyzer/   # regex, энтропия, контекст, scoring, route
    feed/              # лента задач (claim, lease, retry)
    orchestrator/      # запуск анализа: план, fan-out, завершение
    workers/           # демоны: commit worker, ai worker
    ai_validation/     # маскирование, prompt, LLM, вердикт
    incident_manager/  # решение об инциденте, дедупликация, жизненный цикл
    storage/           # SQL, миграции, транзакции
    observability/     # логи и метрики
  tests/
```

## 4. Разделение ответственности (не нарушать)

| Модуль | Делает | НЕ делает |
|---|---|---|
| `git_collector` | достаёт SHA и diff | не анализирует содержимое |
| `preprocessor` | diff → строки → `RawCandidate` | не считает риск, не ходит в БД и LLM |
| `static_analyzer` | признаки, score, route → `Candidate` | не пишет в БД, не создаёт задачи |
| `feed` | хранит и выдаёт `Task` | не знает про детекторы |
| `orchestrator` | планирует запуск, закрывает его | не анализирует код |
| `ai_validation` | маскирует, зовёт LLM, валидирует ответ | не решает про инцидент |
| `incident_manager` | решает про `Incident`, дедуплицирует | не ходит в LLM и Git (кроме проверки HEAD через `git_collector`) |
| `storage` | персистентность, транзакции | не содержит бизнес-логики |
| `models` | данные и поведение самой модели | не содержит SQL, сети, чтения конфигурации |

## 5. Правила моделей

1. **Одна модель — один класс — один файл** в `src/models/`. Enum, принадлежащий одной модели, живёт в её файле; общие (`SecretType`, `Severity`, `DetectorFlags`) — в `models/enums.py`.
2. **Первичный ключ — всегда `id: int`** (`INTEGER PRIMARY KEY`). Строковые PK запрещены. Внешние ключи — `int`.
3. **Естественные ключи** (SHA коммита, fingerprint секрета, `idempotency_key`) — `bytes` с `UNIQUE`-индексом, не PK. В логах и UI — hex.
4. Enum — `IntEnum`/`IntFlag` с закреплёнными числовыми значениями (в БД `SMALLINT`); значения не менять и не переиспользовать.
5. Время в коде — `datetime` UTC (tz-aware); в БД — epoch в миллисекундах.
6. Каждое поле в `docs/models.md` имеет Python-тип и тип в БД; **не пропускай и не добавляй поля молча** — сначала правка документа.
7. JSON-колонки — только для данных, по которым не ищут (payload, output, metrics).
8. Сырое значение секрета — только в `RawCandidate` (память). Ни в одной сохраняемой модели такого поля быть не должно.

## 6. Инварианты (критично)

1. **Сырой секрет не покидает память процесса.** Не писать в БД, логи, исключения, метрики, `repr()`, тестовые фикстуры. В моделях только `value_masked` и `value_fingerprint` (HMAC-SHA256, ключ из окружения).
2. **В LLM уходят только маскированные значения** (`AKIA...MPLE`). Должен быть флаг полного отключения внешних LLM (`ai.enabled = false`); система обязана работать без LLM.
3. **Идемпотентность.** Повторная обработка не создаёт дублей. Обеспечивается `UNIQUE`-ограничениями: `tasks.idempotency_key`, `candidates(commit_id, file_path, line_number, value_fingerprint)`, `incidents(repository_id, fingerprint)`, `commits(repository_id, sha)`.
4. **Состояние строится по SHA** (`Commit.status`), не по дате и не по `last_processed_commit`: Git — граф (merge, rebase, force-push).
5. **Event loop не блокируется.** I/O — `async`; CPU-bound — `asyncio.to_thread` / `ThreadPoolExecutor`.
6. **Backpressure.** Внутренние очереди ограничены (`maxsize`); вызовы LLM — под `asyncio.Semaphore`.
7. **Ошибка не валит запуск.** Ошибка коммита → `Commit.FAILED`; ошибка файла → пропуск файла; ошибка LLM → retry, затем `AI_VALIDATION` в `FAILED`, запуск получает `Outcome.PARTIAL`.
8. **Атомарность.** Сохранение кандидатов + постановка `AI_VALIDATION` + обновление `Commit.status` + `TaskResult` — одна транзакция. Так же для `AI_VALIDATION` (вердикт + инцидент + outbox + результат).
9. **Пороги и коэффициенты — в конфиге**, не в коде.
10. **Вердикт LLM валидируется** (схема, диапазоны) до использования. Невалидный ответ — ошибка попытки (`LLM_INVALID_RESPONSE`), а не «не секрет».
11. **Статусы меняются только через методы модели** (`Task.transition`, `Incident.set_status`), не прямой записью поля.

## 7. Как делать типовые изменения

**Добавить детектор (regex/формат токена)**
1. Правило в `static_analyzer` с `SecretType`, regex и весом (вес из конфига).
2. Тесты: минимум 3 положительных, 3 отрицательных примера (UUID, hash, placeholder).
3. Если формат надёжен сам по себе — добавить в `IncidentPolicy.trusted_formats` (осознанно: это путь к инциденту без LLM).

**Добавить новую модель или поле**
1. Описать в `docs/models.md`: класс, таблица, все поля с Python-типом и типом в БД, ключи, индексы, связи.
2. Файл в `src/models/`, миграция в `storage/`.
3. Обновить `docs/modules.md`, если меняется поведение модулей.

**Добавить новый вид задачи**
1. `TaskKind` (новое числовое значение), payload/output-классы, допустимые переходы, приоритет по умолчанию.
2. Worker в `workers/`.
3. Правило `idempotency_key` — обязательно в описании изменения.

**Изменить prompt LLM**
1. Увеличить `prompt_version` (входит в `idempotency_key`: старые вердикты не переиспользуются молча).
2. Обновить тесты разбора ответа.

## 8. Тестирование

- Unit: детекторы, энтропия, scoring, переходы статусов `Task` и `Incident`, решение об инциденте.
- Integration: временный git-репозиторий (с merge и force-push), БД в памяти, **фейковый `LlmClient`** (реальных вызовов в тестах нет).
- Обязательные сценарии: первый запуск → повторный не создаёт дублей; падение worker'а посреди пачки (аренда истекла → задача перевыдана); LLM недоступен → `Outcome.PARTIAL`; один секрет в трёх коммитах → один `Incident` с тремя `Occurrence`; закрытый инцидент при повторном обнаружении → reopen.
- Фикстуры с «секретами» используют публичные примеры (`AKIAIOSFODNN7EXAMPLE`) или генерируются в тесте.

## 10. Чего НЕ делать

- Не передавать в LLM весь файл, коммит или репозиторий — только кандидат с локальным контекстом.
- Не считать высокую энтропию или совпадение regex достаточным основанием для инцидента (кроме `trusted_formats`).
- Не использовать `git log --since` или «последний SHA» как состояние.
- Не использовать строки как PK и не хранить SHA/fingerprint как hex-текст.
- Не добавлять глобальное состояние и синглтоны; зависимости передаются явно.
- Не логировать `source_line` без маскирования.
- Не смешивать слои (§4): если хочется, нужен новый интерфейс, а не обход.
